# Agent Setup

## 目的

このドキュメントは、このリポジトリでコーディングエージェントを安全かつ効率的に動かすために入れたルール・設定と、その意図をまとめたものである。

## 用意したファイル

- `CLAUDE.md`
- `docs/spec-template.md`

## 入れたルール・設定とその意図

### 1. レイヤ構成を前提にしたルール

**ルール**
- `api` は HTTP の責務に集中する
- `services` はユースケースのオーケストレーションを持つ
- `domain` はエンティティ、ルール、抽象を持つ
- `infra` は DB や外部APIなど外部依存を持つ

**意図**
- Router に業務ロジックが漏れることを防ぐ
- 既存のアーキテクチャ方針と整合させる
- 変更時の影響範囲を小さくする

### 2. 非同期実行の境界に関するルール

**ルール**
- 非同期起動方式の変更は `ExecutionDispatcher` を境界に行う
- `BackgroundTasks` などの具体実装を Router に直接持ち込まない

**意図**
- 現状は MVP として in-process 実装を維持しつつ、将来のワーカーキュー移行を容易にする
- 実行方式の変更が API 層へ波及しにくいようにする

### 3. ノード拡張に関するルール

**ルール**
- ノード追加時は `NodeType`、processor、registry、NodeSpec をセットで管理する
- ノード固有設定の検証は processor 側に寄せる
- ノードの入出力制約は `NodeSpec` / `WorkflowRules` で扱う

**意図**
- 新しいノード追加時に中心ロジックの分岐が肥大化するのを防ぐ
- ノード追加者が触るべき範囲を明確にする

### 4. ドキュメント整合性に関するルール

**ルール**
- API やセットアップを変えたら README 更新を検討する
- 設計意図に関わる変更をしたら ADR 更新を検討する
- `.env` の追加項目は `.env.example` に反映する

**意図**
- 実装とドキュメントの乖離を防ぐ
- 他の開発者や将来のエージェントが現在地を誤解しないようにする

### 5. 検証を必須とするルール

**ルール**
- 変更後は少なくとも構文チェックかビルド確認を行う
- バックエンドなら `compileall`、フロントエンドなら `npm run build` を最低ラインとする

**意図**
- AIエージェントによる編集ミスを早期に検出する
- 「編集だけして未検証」の状態を減らす

## この構成にした理由

今回のリポジトリは、課題1で実装したアプリケーションがすでに一定の構造を持っている。そのため、課題2では「新しいアーキテクチャを提案する」よりも、「既存構造を壊さずにエージェントが開発しやすくする」ことを重視した。

特に重要視した点は以下である。

- 既存のレイヤ分割と責務分離を維持できること
- ノード追加時の影響範囲を局所化できること
- 非同期実行基盤の変更余地を残せること
- README / ADR / 実装の整合を保てること

## 使い方

1. エージェントはまず `CLAUDE.md` を読む
2. 新規開発タスクを依頼するときは `docs/spec-template.md` をベースに仕様を書く
3. 変更後は README、ADR、環境変数、検証コマンドの更新要否を確認する
