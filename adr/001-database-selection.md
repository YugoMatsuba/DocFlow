# ADR-001: データストアの選定

## 背景・解決したい課題

このプロダクトでは、ワークフロー定義、ノード設定、実行履歴を永続化し、後から状態や結果を参照できる必要がある。初期コードベースはインメモリ管理を前提としていたため、以下の課題があった。

- サーバー再起動でデータが消える
- 複数ユーザー利用時の整合性を担保しづらい
- 実行履歴や状態遷移を継続的に追跡しづらい
- 将来の利用拡大を見据えたデータ管理基盤として弱い

また、課題1では以下も同時に満たす必要がある。

- 外部データストアによる永続化
- マイグレーション可能なスキーマ管理
- ノードごとに異なる設定を無理なく保持できること
- ワークフロー、ノード、実行履歴の関係を扱いやすいこと

## 決定事項

永続化のデータストアとして **PostgreSQL** を採用し、アプリケーションからのアクセスには **SQLAlchemy**、スキーマ変更管理には **Alembic** を採用する。

現時点の構成は以下とする。

- PostgreSQL: ワークフロー、ノード、実行履歴の永続化
- SQLAlchemy: ORM と repository 実装
- Alembic: マイグレーション管理
- ノード設定: JSON カラムを用いて柔軟に保持
- ファイル本体: DB ではなくローカルストレージに保存し、DB には参照情報を持たせる

## 選択肢

### Option1: PostgreSQL

👍**Pros**

- リレーショナルなデータ構造を自然に扱える
- 実行状態や履歴に対して一貫性を持たせやすい
- JSON / JSONB によりノード設定の柔軟性を確保しやすい
- SQLAlchemy / Alembic との相性が良く、Python から扱いやすい
- 将来的な検索、集計、インデックス最適化の余地がある

👎**Cons**

- SQLite よりセットアップは重い
- 小規模MVPとしては運用要素が一段増える
- SQL と RDB 設計の前提知識が必要になる

### Option2: MongoDB

👍**Pros**

- ドキュメント指向で、ノード設定の保存は直感的
- スキーマ変更に比較的柔軟
- JSON ライクなデータをそのまま扱いやすい

👎**Cons**

- ワークフロー、ノード、実行履歴の関係を横断して扱う設計では、整合性や問い合わせの見通しが悪くなりやすい
- 課題1で必要な「状態管理」「履歴管理」を説明する上で、今回の用途にはやや過剰に柔軟
- 現在のアプリケーション構造では、RDB の方がモデル化しやすい

### Option3: SQLite

👍**Pros**

- セットアップが最も簡単
- ローカル開発に向いている
- 小規模な単体アプリなら十分実用的

👎**Cons**

- 書き込み競合に弱く、同時実行が増えると制約が出やすい
- 実行履歴や非同期実行を含む用途では、将来の拡張余地が小さい
- 本番相当の構成としては PostgreSQL より先に限界が来やすい

### Option4: MySQL

👍**Pros**

- 成熟した RDB であり、安定運用しやすい
- 一般的な CRUD や並行利用には十分強い
- 運用ノウハウを持つチームも多い

👎**Cons**

- 今回の JSON 活用や柔軟な問い合わせでは PostgreSQL の方が扱いやすい
- Python / SQLAlchemy / Alembic 前提で比較したとき、今回の課題では PostgreSQL の方が説明しやすい
- 今回の用途に対して、MySQL を選ぶ積極的な理由が弱い

## 懸念事項・影響範囲

- **初期コスト**: インメモリ実装よりセットアップと運用は重くなる
- **スキーマ設計**: ワークフロー、ノード、実行履歴の関係を適切に切る必要がある
- **ファイル保存の分離**: PDF 本体は DB に直接保存せず、別ストレージとの責務分離を維持する必要がある
- **テスト戦略**: repository や DB 依存の振る舞いを検証するため、永続化を前提にしたテストが必要になる
- **将来の拡張**: 現時点では PostgreSQL で十分だが、ファイルストレージや検索要件が大きくなれば別コンポーネントの追加も検討余地がある
