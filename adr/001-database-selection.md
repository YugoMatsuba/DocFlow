# ADR-001: データストアの選定

## 背景・解決したい課題

このプロダクトでは、ワークフロー定義、ノード設定、実行履歴を永続化し、後から状態や結果を参照できる必要がある。初期コードベースはインメモリ管理を前提としていたため、以下の課題があった。

- サーバー再起動でデータが消える
- 複数ユーザー利用時の整合性を担保しづらい
- 実行履歴や状態遷移を継続的に追跡しづらい
- 将来の利用拡大を見据えたデータ管理基盤として弱い

また、課題1では以下も同時に満たす必要がある。

- 外部データストアによる永続化
- マイグレーション可能なスキーマ管理
- ノードごとに異なる設定を無理なく保持できること
- ワークフロー、ノード、実行履歴の関係を扱いやすいこと

## 決定事項

永続化のデータストアとして **PostgreSQL** を採用し、アプリケーションからのアクセスには **SQLAlchemy**、マイグレーションには **Alembic** を採用する。

現時点の構成は以下とする。

- PostgreSQL: ワークフロー、ノード、実行履歴の永続化
- SQLAlchemy: ORM と repository 実装
- Alembic: マイグレーション管理
- ノード設定: JSON カラムを用いて柔軟に保持
- ファイル本体: DB ではなくローカルストレージに保存し、DB にはファイルパスを持たせる

採用理由は以下とする。

- PostgreSQL: ワークフロー、ノード、実行履歴のような関係性を持つデータを自然に扱え、状態管理の一貫性も取りやすい
- SQLAlchemy: Python エコシステムで広く使われている標準的な ORM であり、Workflow と Node の関係や Execution の状態遷移を表現しやすい。FastAPI と組み合わせやすく、AsyncSession も利用できるため、現在のアプリケーション構成に乗せやすい
- Alembic: SQLAlchemy と組み合わせるマイグレーションツールとして定番であり、スキーマ変更を履歴として管理しやすい。Python で利用例や情報量が多く、セットアップや運用を学習しやすい

アクセス方式とスキーマ変更管理では、以下も比較した。

- **SQLAlchemy + Alembic**
  - Python では実質的に標準寄りの選択肢で、知っている開発者が多い
  - 情報量や実装例が多く、学習コストを抑えやすい
  - repository パターンや現在のレイヤ構成でも使いやすい
- **手書き SQL + 手書きマイグレーション**
  - SQL を完全に制御でき、抽象化の振る舞いを気にしなくてよい
  - 一方で CRUD やリレーション操作の記述量が増えやすく、実装の重複も起きやすい
  - スキーマ変更履歴も自前で厳密に管理する必要があり、変更漏れや実装差分のリスクが上がる
  - MVP で必要な実装速度、保守性、説明しやすさまで含めると、今回は標準的な `SQLAlchemy + Alembic` の方が適している

## DB選択肢

### Option1: PostgreSQL

👍**Pros**

- リレーショナルなデータ構造（ワークフローとノードの関係性）を自然に扱える
- 実行状態や履歴に対して一貫性を持たせやすい
- JSON / JSONB によりノード設定の柔軟性を確保しやすい
- SQLAlchemy / Alembic との相性が良く、Python から扱いやすい

👎**Cons**

- SQLite よりセットアップは重い
- 小規模MVPとしては運用要素が一段増える
- SQL と RDB 設計の前提知識が必要になる

### Option2: MongoDB

👍**Pros**

- ドキュメント指向で、ノード設定の保存は直感的
- スキーマレス
- JSON ライクなデータをそのまま扱いやすい

👎**Cons**

- ワークフロー、ノード、実行履歴の関係性をテーブルと比べて表しづらい
- 保存する「ステータス」や「履歴」といったデータはスキーマが決まっている

### Option3: SQLite

👍**Pros**

- セットアップが最も簡単
- ローカル開発に向いている
- 小規模な単体アプリなら十分実用的

👎**Cons**

- ファイルロックにより、複数の同時の書き込みができず、レイテンシーが遅くなる
- 本番相当の構成としては将来の拡張余地が少なく PostgreSQL より先に限界が来やすい

### Option4: MySQL

👍**Pros**

- 成熟した RDB であり、安定運用しやすい
- 一般的な CRUD や並行利用には十分強い
- 運用ノウハウを持つチームも多い

👎**Cons**

- 今回の JSON 活用や柔軟な問い合わせでは PostgreSQL の方が扱いやすい

## 懸念事項・影響範囲

- **スキーマ設計**: ワークフロー、ノード、実行履歴の関係を適切に切る必要がある
- **ファイル保存の分離**: PDF 本体は DB に直接保存せず、別ストレージとの責務分離を維持する必要がある
