# ADR-001: データベース技術選定

## 背景・解決したい課題

LayerXワークフローシステムのMVPにおいて、永続化データストレージ技術の選定が必要となった。

現在の実装では以下の課題が存在する：
- **データの永続性不足**: インメモリストレージ（`workflows = {}`）によりサーバー再起動時にデータが消失
- **並行処理への対応不可**: 複数ユーザーの同時アクセスに対する整合性保証なし
- **実行履歴の未対応**: ワークフロー実行の状態追跡や履歴管理ができない
- **スケーラビリティの制約**: 1チーム（5〜10名）から他部署展開時の拡張性不足

また、仕様要件として以下が求められている：
- 外部データストア（PostgreSQL、MongoDB、SQLiteファイルモード等）を用いた永続化
- スキーマの変更管理（マイグレーション）が可能な仕組み
- ノード設定の柔軟性（多様な入出力への対応）
- 将来的な同時実行数増加への対応

## 決定事項

**PostgreSQL** をデータベースとして採用する

**データ構成:**
- **Primary Database**: PostgreSQL（ワークフロー、ノード、実行履歴の永続化）
- **ORM**: SQLAlchemy 2.0（型安全性とAsync対応）
- **Migration**: Alembic（スキーマ変更管理）

## 選択肢

### Option1: PostgreSQL

👍**Pros**
- **ACID準拠**: ワークフロー実行状態の強い一貫性を保証
- **優秀な関係性サポート**: Workflow → Node → WorkflowExecution の階層構造に最適
- **JSONBサポート**: ノード設定の柔軟性と構造化データのバランスが取れる
- **成熟したエコシステム**: SQLAlchemy、Alembic等の充実した開発ツール
- **優秀な並行処理**: マルチユーザー環境での競合状態を適切にハンドリング
- **全文検索とインデックス**: ワークフロー検索とパフォーマンス最適化が可能

👎**Cons**
- セットアップの複雑さ（Docker環境での運用が必要）
- 小規模環境でのリソース使用量
- 初期学習コスト

### Option2: MongoDB

👍**Pros**
- 柔軟なスキーマでノード設定の多様性に対応しやすい
- JSON文書の自然な保存
- 水平スケールの容易さ

👎**Cons**
- **コレクション間ACIDトランザクション未対応**: ワークフロー実行状態の一貫性に課題
- 複雑なリレーションシップの管理困難
- 参照整合性の手動管理が必要
- SQLベースの運用ノウハウが活用できない

### Option3: SQLite

👍**Pros**
- セットアップの簡単さ
- ファイルベースで管理が容易
- 軽量で開発初期に適している

👎**Cons**
- **並行書き込みの制限**: 複数ユーザー同時アクセス時に性能劣化
- スケーラビリティの根本的制約（他部署展開時に対応不可）
- JSON処理能力の制限
- 運用監視ツールの不足

### Option4: MySQL

👍**Pros**
- 高い互換性と安定性
- 豊富な運用ノウハウ
- 良好な並行処理性能

👎**Cons**
- JSONサポートがPostgreSQLより限定的（ノード設定の柔軟性に制約）
- 複雑なクエリやインデックス戦略でPostgreSQLに劣る
- 全文検索機能の制限

## 懸念事項・影響範囲

### 技術的懸念事項
- **初期パフォーマンス**: 小規模MVPでのオーバーエンジニアリングリスク
- **学習コスト**: チーム内でのPostgreSQL運用スキルの必要性

### 影響を受けるコンポーネント
- **既存のPydanticモデル**: SQLAlchemyモデルへの移行が必要
- **API層**: データアクセス層の抽象化（Repository パターン導入）
- **テスト戦略**: データベーステストの環境構築

### 移行の必要性
- **段階的移行**: 現在のインメモリ実装から段階的にPostgreSQLへ移行
- **データモデル設計**: 3テーブル構成（workflows, nodes, workflow_executions）での設計
- **マイグレーション戦略**: Alembic導入によるスキーマ変更管理体制の確立

### リスク軽減策
- **Repository パターン**: データアクセス層の抽象化によるテスタビリティ向上
