# ADR-007: 複数 PDF ドキュメント入力の扱い

## 背景・解決したい課題

このアプリケーションでは、PDF を入力としてワークフローを実行する。運用を考えると、1 件の PDF だけでなく、複数の PDF ドキュメントをまとめて扱いたいケースも想定される。

このとき、複数 PDF をどの単位で API に載せるかを決める必要がある。主な論点は以下である。

- 1 execution を 1 つの入力ドキュメントとしてシンプルに保つか
- 複数 PDF を 1 回の API リクエストでまとめて扱えるようにするか
- 結果参照、失敗時の再実行、ユーザー操作の負担をどう整理するか

MVP の段階では、入力モデルを過度に複雑にせず、Execution の意味を明確に保つことを優先したい。

## 決定事項

**MVP では、1 execution = 1 PDF を基本とし、複数 PDF を扱う場合は複数の API リクエストに分ける**。

現時点の方針は以下とする。

- `POST /api/executions/` は 1 つの PDF ファイルを受け取る
- 複数 PDF を個別に処理したい場合は、Execution を複数作成する
- 複数 PDF を 1 つの入力として扱いたい場合は、ユーザー側で PDF を結合してからアップロードする
- サーバー側で複数 PDF を 1 execution に束ねる API は導入しない

この判断により、Execution の単位、状態管理、失敗時の扱いをシンプルに保つ。

## 選択肢

### Option1: 複数 PDF は複数の API リクエストに分ける

👍**Pros**

- `1 execution = 1 入力` というモデルを保てる
- 実行状態、失敗、再実行の単位が明確になる
- 現在の単一 PDF 前提の処理フローをそのまま利用できる
- 複数 PDF を 1 つにまとめたい場合は、ユーザー側でファイルを結合するだけで対応できる
- 個別の PDF ごとに結果を見たいケースと相性が良い

👎**Cons**

- 複数 PDF をまとめて実行したい場合は、クライアント側で作業が必要になる

### Option2: 複数 PDF を 1 回の API リクエストでまとめて扱う

👍**Pros**

- ユーザーは一度の操作で複数 PDF を送信できる
- バッチ投入の体験はわかりやすい
- 将来的な一括処理の入り口として見せやすい

👎**Cons**

- 1 execution が 1 つの結果なのか、複数結果の集合なのかが曖昧になる
- 失敗時に「どの PDF が失敗したか」「どこから再実行するか」の設計が複雑になる
- 複数 PDF を本来別々に処理したい場合に、ユーザーの作業が多くなる

## 懸念事項・影響範囲

- **UX の制約**: 複数 PDF を一括投入したい場合、クライアント側で複数リクエストを扱う必要がある
- **入力モデルの明確さ**: 現時点では単一 PDF 入力に寄せることで、Execution の意味をシンプルに保てる
- **将来拡張**: 本当に一括投入の需要が高まった場合は、batch execution のような別 resource を追加する余地がある
- **ユーザー負担のバランス**: 複数 PDF を 1 つにまとめたいケースではファイル結合だけで対応できる一方、最初から 1 リクエスト多入力にすると、個別処理したいケースでのユーザーの負担が大きくなる
