# ADR-003: ソフトウェアアーキテクチャ

## 背景・解決したい課題

このプロダクトには、ワークフロー定義、ノード追加、実行履歴、ファイル保存、AI 連携など、性質の異なる責務が複数存在する。さらに、将来的には運用チームが新しいノードタイプを追加していくことも想定している。

初期実装の速度は重要だが、責務が一箇所に集中した構造にすると、ノード追加や非同期実行方式の変更のたびに影響範囲が広がる。特に、Router や中心サービスに処理が寄りすぎる構造は避けたかった。

## 決定事項

**レイヤードアーキテクチャを採用し、DDD の概念を一部取り入れた構成にする**。

責務分離の方針は以下とする。

- `api/`: HTTP ルーティング、Schema、Dependency Injection
- `services/`: ユースケースのオーケストレーション
- `domain/`: Entity、Enum、Repository interface、Rule、Spec
- `infra/`: DB、外部 API、ファイル保存など外部依存の具体実装

この構成により、以下を狙う。

- 高凝集: 各レイヤーが明確な責務を持つ
- 疎結合: 上位層が具体実装に直接依存しない
- 拡張容易性: ノード追加や実行基盤変更の影響範囲を局所化する
- テスタビリティ: repository や dispatcher を差し替えやすくする

## 選択肢

### Option1: レイヤードアーキテクチャ + DDD 概念の部分採用

👍**Pros**

- 責務分離がわかりやすい
- MVP として現実的な複雑さに収まる
- domain rule や repository interface を独立させやすい
- ノード追加や非同期基盤の変更を説明しやすい
- チーム開発で影響範囲を追いやすい

👎**Cons**

- フラット構成よりファイル数は増える
- 層をまたぐデータ変換の手間がある
- 厳密な DDD ほど用語や境界を統制しているわけではない

### Option2: フラットな構成に寄せる

👍**Pros**

- 初期実装は速い
- 学習コストが低い
- 小さなサンプルなら把握しやすい

👎**Cons**

- Router や Service に責務が集中しやすい
- ノード追加時に変更箇所が散りやすい
- 将来的な変更で密結合になりやすい
- 設計判断を説明しづらい

### Option3: 厳密な Clean Architecture にする

👍**Pros**

- 境界がより明確になる
- 外部依存の差し替えにより強い
- 長期的な保守性は高い

👎**Cons**

- MVP にはやや重い
- 抽象や DTO が増えやすい
- 実装速度を落とす可能性がある

## 懸念事項・影響範囲

- **Service の肥大化**: ユースケースが増えると application service に処理が集まりやすい
- **抽象の増やしすぎ**: MVP に対して過度な抽象化は避ける必要がある
- **一貫性維持**: 新規機能追加時にも同じ責務分離を守らないと設計が崩れやすい
- **将来の移行**: 必要ならより厳密なクリーンアーキテクチャへ寄せられるが、現時点では実装速度とのバランスを優先する
