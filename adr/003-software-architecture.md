# ADR-003: ソフトウェアアーキテクチャ

## 背景・解決したい課題

このプロダクトでは、ワークフロー、ノード、実行履歴、ファイル保存、AI連携など、異なる責務を持つ機能が同時に存在する。さらに今後は、運用チームがノード種別を増やしていくことも想定されている。

そのため、初期実装の速度を確保しつつも、責務が一箇所に密集した「変更しづらいコード」にはしたくない。特に、ノード追加者がアプリケーション全体に強く依存しなくて済む構造が必要だった。

## 決定事項

**レイヤードアーキテクチャを採用し、DDDの概念を一部取り入れた構成にする**。

具体的には以下の責務分離を採用する。
- `api/`: HTTPルーティング、リクエスト/レスポンス、依存注入
- `services/`: アプリケーションサービス、ユースケースのオーケストレーション
- `domain/`: Entity、Enum、Repository interface、Rule、Spec
- `infra/`: DB実装、OpenAIクライアント、ファイルストレージなど外部依存

この構成により、以下を狙う。
- 高凝集: 各モジュールが明確な責務を持つ
- 疎結合: 上位層が外部実装の詳細を直接知らない
- 拡張容易性: ノード追加や実行基盤変更の影響範囲を局所化する
- テスタビリティ: repository や dispatcher を抽象化し差し替えやすくする

## 選択肢

### Option1: レイヤードアーキテクチャ + DDD概念を部分採用

👍**Pros**
- 責務分離がわかりやすい
- FastAPIベースのMVPとして現実的
- domain rule や repository interface を独立させやすい
- ノード追加や非同期実行の差し替えを説明しやすい
- チーム開発で影響範囲を追いやすい

👎**Cons**
- 小規模MVPとしてはファイル数が増える
- 層をまたぐデータ変換の手間がある
- 厳密なDDDほど統一された用語体系にはなっていない

### Option2: フラットな構成に寄せる

👍**Pros**
- 初期実装が速い
- 学習コストが低い
- 小規模なサンプルなら読みやすい

👎**Cons**
- RouterやServiceに責務が集中しやすい
- ノード追加時に変更箇所が散りやすい
- 将来的な変更で密結合になりやすい
- 課題1で期待される設計判断の説明が弱くなる

### Option3: 厳密なClean Architectureにする

👍**Pros**
- 境界がより明確
- 外部依存の差し替えに強い
- 長期的な保守性は高い

👎**Cons**
- MVPにはやや重い
- 抽象やDTOが増えやすい
- 初期段階での実装速度を落とす可能性がある

## 懸念事項・影響範囲

- **Service肥大化**: application service に処理が集まりすぎると再び責務が曖昧になる
- **抽象の増やしすぎ**: MVPに対して過度な抽象化は避ける必要がある
- **一貫性維持**: 新規機能追加時にも同じ責務分離を守らないと設計が崩れやすい
- **移行余地**: 将来さらに厳密なクリーンアーキテクチャへ寄せることは可能だが、現時点では実装速度とのバランスを優先する
