# ADR-006: 実行状態確認のリアルタイム性

## 背景・解決したい課題

このアプリケーションでは、ワークフロー実行に数秒から数分かかる場合がある。そのため、ユーザーは実行開始後にブラウザを閉じ、後から状態や結果を確認することがある。

一方で、初期ユーザー規模は小さく、MVP の段階で高度なリアルタイム通知基盤を最初から整える必要があるかは慎重に判断したい。このアプリケーションで重要なのは、チャットのような即時性ではなく、「後から確実に結果を確認できること」を先に満たすことである。

## 決定事項

**MVP 段階では、Execution 状態の確認は手動リロードまたは明示的な再取得を前提とする**。

現時点の方針は以下とする。

- 実行状態は DB に永続化する
- 一覧画面・詳細画面から状態取得 API を呼んで確認する
- ポーリングや SSE は導入しない
- 必要性が明確になった段階でポーリング、さらに必要なら SSE を検討する

この判断は、ドキュメント処理パイプラインという用途において、MVP ではリアルタイム性よりも「結果をあとで見に来られること」の方が重要だと考えたためである。

## 選択肢

### Option1: 手動リロード / 明示的な再取得

👍**Pros**

- 実装が最もシンプル
- サーバー負荷が低い
- クライアント実装が単純
- MVP の要件を十分満たす

👎**Cons**

- ユーザーが自分で更新操作を行う必要がある
- リアルタイム性は最も低い

### Option2: 定期ポーリング

👍**Pros**

- 実装コストが比較的低い
- ある程度のリアルタイム感を出せる
- SSE より導入しやすい

👎**Cons**

- 不要なリクエストが増える
- 短い間隔だとサーバー負荷が上がる
- 長い間隔だと体験が中途半端になりやすい
- 実行ステータスの変化自体頻繁に大量に変わるわけでもない

### Option3: Server Side Event

👍**Pros**

- 実行完了を即時反映しやすい
- リアルタイム体験としては最も優れている

👎**Cons**

- MVP としては実装と運用が重い
- 接続管理やエラー処理が増える
- 初期利用シナリオに対して過剰になりやすい

## 懸念事項・影響範囲

- **UX の限界**: 現状はユーザーが自分で状態確認を行う必要がある
- **将来移行**: 状態は execution resource に集約しているため、将来ポーリングや SSE へ進化させやすい
- **用途との整合**: 現在の用途では即時通知よりも結果参照の確実性を優先している
- **再検討条件**: 同時利用者増加、長時間ジョブ増加、オペレーション用途の強化が起きた時点で自動更新の必要性を再評価する
