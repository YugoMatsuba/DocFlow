# ADR-004: ノード処理の拡張方式

## 背景・解決したい課題

このアプリケーションでは、`EXTRACT_TEXT`、`GENERATIVE_AI`、`FORMATTER` 以外にも、将来新しいノードタイプが追加されることが想定されている。ノードごとに必要な設定や入出力の型が異なるため、ノード追加時にコアロジックを大きく書き換える構造は避ける必要がある。

特に避けたいのは、ワークフロー実行ロジックに巨大な `if/elif` 分岐を置き続ける設計である。これではノード種別が増えるほど結合が強まり、実装者が既存コード全体を触らざるを得なくなる。

## 決定事項

**Strategyデザインパターンを使い各ノード処理を分離し、共通インターフェースを通して実行する**。

具体的には以下の構成を採用する。
- 各ノード処理は `BaseNodeProcessor` を実装する
- `ProcessorRegistry` が `NodeType` と具体プロセッサを対応付ける
- `NodeSpec` / `NodeSpecRegistry` で入出力型や必須設定などの制約を別管理する
- ワークフロー実行側は `NodeType` ごとの具体実装詳細を直接知らず、registry 経由で処理する

この構成により、ノード追加時の変更点を以下に限定しやすくする。
- 新しい `NodeType` の追加
- 対応する processor の追加
- 必要に応じた `NodeSpec` の追加

## 選択肢

### Option1: Processor registry + 共通インターフェース + NodeSpec

👍**Pros**
- 実行側の分岐を増やしにくい
- ノード追加者が追加対象を理解しやすい
- 設定検証と実処理をノード単位で閉じ込められる
- 入出力制約を `NodeSpec` に分離できる
- Strategy パターンとして説明しやすい

👎**Cons**
- registry 登録漏れの管理が必要
- 動的に増える分、IDE上での参照がやや追いづらいことがある
- processor と spec の二重管理が発生しうる

### Option2: 実行サービス内で `if/elif` 分岐する

👍**Pros**
- 実装が最も単純
- 小さなサンプルでは理解しやすい

👎**Cons**
- ノード追加のたびに中心ロジックを触る必要がある
- 結合が強くなる
- 設定検証や入出力制約が散らばりやすい
- 実行エンジンが肥大化しやすい

## 懸念事項・影響範囲

- **型安全性**: 現在は Python の動的性質上、入出力型はランタイム検証中心になる
- **SpecとProcessorの整合性**: 新ノード追加時に両方を更新する規律が必要
- **柔軟性と単純さのバランス**: plugin system ほどの汎用性はないが、MVPとしては十分な拡張点を持てる
- **将来拡張**: 新しいファイル型や構造化データを扱う場合も、`NodeSpec` 側のI/O制約を広げることで対応しやすい
