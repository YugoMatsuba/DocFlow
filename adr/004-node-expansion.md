# ADR-004: ノード処理の拡張方式

## 背景・解決したい課題

このアプリケーションでは、`EXTRACT_TEXT`、`GENERATIVE_AI`、`FORMATTER` 以外にも、将来的に新しいノードタイプが追加される可能性がある。ノードごとに必要な設定や入出力の性質が異なるため、ノード追加のたびにコアの実行ロジックを大きく変更する構造は避けたい。

特に避けたいのは、ワークフロー実行側に巨大な `if/elif` 分岐を持たせ続ける設計である。この形ではノード種別が増えるほど中心ロジックへの依存が強くなり、追加コストもレビューコストも上がる。

## 決定事項

**Strategy パターンをベースに、各ノード処理を共通インターフェースの背後に分離する**。

現時点の構成は以下とする。

- 各ノード処理は `BaseNodeProcessor` を実装する
- `ProcessorRegistry` が `NodeType` と具体プロセッサを対応付ける
- `NodeSpec` / `NodeSpecRegistry` で入出力制約や必須設定を別管理する
- ワークフロー実行側は registry 経由で processor を取得し、異なる種類のノードの具体実装に直接依存しない

この構成により、新しいノード追加時の変更点を局所化しやすくする。

## 選択肢

### Option1: Processor registry + 共通インターフェース + NodeSpec

👍**Pros**

- 実行側の分岐を増やしにくい
- ノード追加者の影響範囲が明確になる
- 設定検証と実処理をノード単位で閉じ込められる
- 入出力制約を `NodeSpec` に分離できる

👎**Cons**

- registry への登録漏れを防ぐ運用が必要
- processor と spec の整合性を保つ必要がある

### Option2: 実行サービス内で `if/elif` 分岐する

👍**Pros**

- 実装が最も単純
- 小さなサンプルでは把握しやすい

👎**Cons**

- ノード追加のたびに中心ロジックを変更する必要がある
- 結合が強くなる
- 設定検証や入出力制約が散らばりやすい
- 実行エンジンが肥大化しやすい

## 懸念事項・影響範囲

- **型安全性**: Python では入出力検証がランタイム中心になる
- **整合性維持**: 新ノード追加時に `NodeType`、processor、registry、spec をセットで更新する規律が必要
- **柔軟性とのバランス**: plugin system ほど汎用ではないが、MVP としては十分な拡張点を持てる
- **将来拡張**: 新しいファイル型や構造化データを扱う場合も、`NodeSpec` を拡張しやすい
