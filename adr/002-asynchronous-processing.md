# ADR-002: 非同期処理アーキテクチャ

## 背景・解決したい課題

このプロダクトでは、ワークフロー実行に数秒から数分かかる場合がある。そのため、HTTP リクエスト中に処理を同期実行するのではなく、実行を受け付けて後から状態や結果を参照できる構成が必要だった。

一方で、想定ユーザーはまだ少人数であり、MVP 段階では大量の同時実行や高度なジョブ制御までは前提ではない。したがって、最初からワーカーキューや専用ジョブ基盤を導入すると、実装・運用コストが先行しやすい。

ここでは、MVP としての実現性と、将来のスケーラビリティの両立が課題だった。

## 決定事項

MVP 段階では、**FastAPI アプリケーションと同一プロセス内で `BackgroundTasks` を使って非同期実行する**。

ただし、起動方式を Router や Service に直接埋め込まず、`ExecutionDispatcher` で抽象化する。現時点の方針は以下とする。

- Execution 作成後にRunningのステータスで DB へ永続化する
- 永続化後に `ExecutionDispatcher` 経由で非同期起動する
- 実行状態は `workflow_executions` テーブルで管理する
- 実行本体は `ExecutionService` が担当する
- 将来キューへ移行する場合は dispatcher の具体実装を差し替える

## 選択肢

### Option1: API と同一プロセス内で `BackgroundTasks` を使う

👍**Pros**

- MVP として最もシンプルに実装できる
- 追加インフラが不要
- ローカル開発とデバッグが容易
- 非同期実行、状態参照、失敗ハンドリングの要件を満たせる
- dispatcher 抽象を入れておけば将来の移行余地を残せる

👎**Cons**

- API プロセスと実行基盤が分離されていない
- プロセス障害時の継続性が弱い
- 同時実行数が大量に増えると API 応答性が遅くなる

### Option2: 最初からワーカーキューを導入する

👍**Pros**

- API 層と実行基盤を明確に分離できる
- スケールしやすい
- 再試行、遅延実行、監視などを実装しやすい
- 長時間処理との相性が良い

👎**Cons**

- MVP にはやや重い
- Redis や Celery など追加の運用要素が増える
- ローカル開発とデバッグが複雑になる
- 初期ユーザー規模（1チーム 5~10人）に対して過剰設計になりやすい

## 懸念事項・影響範囲

- **可用性**: 現在は API プロセスにワークフローの非同期実行が依存する
- **スケーラビリティ**: 同時実行数の増加に応じて別プロセスワーカー化が必要になる可能性が高い
- **責務分離**: `BackgroundTasks` の詳細は dispatcher 実装に閉じ込め、Router と Service に漏らさない
- **移行容易性**: 将来キュー化する場合、主な変更点は新たな dispatcher の実装になる
- **状態管理**: 実行状態を永続化しているため、次の非同期基盤へ移行しても API モデルは引き継ぎやすい
